## 首屏加载优化（19:55）

用户反馈首次打开会在「加载中...」停留几秒。

**实测（欧洲出口，仅看结构不看绝对值）**：
- 传输体积很小：HTML 9.1KB(br)、docsify.js 48.4KB(br)、vue.css 3.5KB(br)、README.md 4.1KB(br)、_sidebar.md 1.2KB(br)，合计约 66KB。**不是文件大，而是串行往返多**。
- 关键路径 4 趟：HTML → vue.css（`<link>` 在 head 尾部，阻塞渲染）→ docsify.js（body 末尾）→ md 文件 → Vue 渲染。
- **额外阻塞点**：百度统计 hm.js 原来是同步 `<script>`，排在 docsify.js 之后；而 docsify.js 内有 `DOMContentLoaded` 逻辑才启动，所以 hm.js 慢会直接推迟首屏。
- docsify 内部会分别拉 `_coverpage.md`、`_sidebar.md`、`README.md`。

**已改（`index.html`）**：
1. `assets/vue.css` 改为**内联**（删除 `<link>`，样式并入 `<style>`），省掉一次阻塞渲染的往返。
2. head 加 `<link rel="preload" as="script" href="/assets/docsify.js">`，让 JS 与样式并行下载。
3. 百度统计 `hm.js` 改为 `async`（`var _hmt = _hmt || []` 占位脚本保持同步，队列仍生效）。
4. `#app` 里的「加载中...」换成品牌化骨架：`.lrj-boot`（旋转环 + 站点名 + 正在加载内容），样式写在第一个 `<style>` 块内，避免裸文字像卡死。

**校验**：两个 style 块花括号平衡、`.markdown-section/.sidebar/.cover/.lrj-hero` 等关键选择器均在、无残留 vue.css 外链、`window.$docsify` 配置完整、骨架与 preload 存在。无头浏览器在本沙箱被拦，无法截图实测。

**未做（待定）**：
- 静态首屏（把封面 HTML 直接写进 `#app`）可把首屏从 ~2s 降到 ~0，但与 docsify 渲染衔接易闪烁，需谨慎。
- `_headers` 给 `.md` 加短缓存 + prefetch 才能真正省一次往返（当前 md 是 `max-age=0, must-revalidate`，prefetch 会被重新校验，白做）。
- 根本方案：Cloudflare 在中国大陆无节点，要显著提速需 ICP 备案 + 国内 CDN/对象存储，或迁到预渲染的静态站。

**环境**：本会话 agent-browser 已不存在（node 版本目录改为 `22.22.2-6`），Chrome/Edge headless 均被沙箱拦截，无法截图；本地预览仍需用多线程 HTTPServer（端口 3000）。

## resources 页「直接打开店铺」时好时坏排查（23:40）

用户反馈点「直接打开店铺」出现 失败/成功/失败/成功 交替。

**排除本站因素**：`docs/guide/resources.md:223` 只是普通 `<a href="https://xhslink.com/m/AWr1kqYCuNM" target="_blank" rel="noopener">`，无 onclick；`theme/index.mjs` 的 bindTracking / bindCopy / bindLightbox 均不拦截该链接（只读属性、只匹配 `[data-lrj-copy]`、只匹配 `.vp-doc img`）。本站不可能产生"第 N 次点击"状态。

**实测链路**：
- `xhslink.com` 解析到两个 IP（106.54.99.69 / 118.195.253.242），分别测均稳定 302，20 次跳转目标完全一致 → 短链不是变量。
- 302 目标：`https://www.xiaohongshu.com/shop/65994c2c096eae0001305ee2?instation_link=xhsdiscover://shop_detail?...&page_instance=3957&back_chain_id=shop_homepage_share`（TencentEdgeOne CDN）。
- **该落地页服务端约 50/50 返回两种 HTML**：37,482B（含完整 SSR 商品数据，内含 xhsdiscover 商品 link）vs 5,745B（无 SSR 数据空壳）。30 次采样 14:16，尺寸与是否含 xhsdiscover 完全一一对应。两页加载同一份 main.bd6427f.js。
- 「打开店铺失败」文案不在本站仓库中，来自小红书落地页自身；无 SSR 数据那次由前端补请求，失败即弹该提示。

**结论**：用户感知的"奇偶交替"实为 50% 随机，非本站逻辑。`instation_link` 是移动端唤起 App 用的（xhsdiscover://），桌面浏览器点它天然成功率低。

**补充：用户在移动端测试，同样偶发「打开店铺失败」**（说明不是桌面特有问题）。移动端链路多一环：xhslink → 302 → 店铺页 → JS 自动跳 `xhsdiscover://shop_detail?...` 唤起 App。iOS/Android 要求自定义协议必须由用户手势触发，而 `target="_blank"` 把这次手势用在了开标签上，跨域 302 后的自动唤起没有手势 → 被拦 → 落地页弹「打开店铺失败」。叠加落地页 SSR 空壳分流（手机 UA 实测 9:3，桌面 UA 14:16），所以时好时坏。

**已实施（23:45）**：
- `docs/guide/resources.md:223`：静态 href 改为 Web 店铺页 `https://www.xiaohongshu.com/shop/65994c2c096eae0001305ee2`，加 `data-lrj-shop` 与 `data-lrj-event="click_buy_xhs"`（埋点交给已有委托监听，避免桌面端丢统计）。
- `theme/index.mjs` 新增 `bindOpenShop()`：UA 判定移动端时 preventDefault，直接 `location.href = xhsdiscover://shop_detail?seller_id=...&source=share`（手势内唤起，最稳），1.6s 后若页面仍在前台则兜底跳 Web 店铺页；桌面端不拦截，走默认 href。
- `node --check` 通过。**沙箱无法跑 `npm run build`**（Vite 清空 dist/.temp 触发 safe-delete 批量删除保护，124 个文件 > 阈值 50），需用户本机构建验证。

**待验证**：手机上点按钮应直接进 App；微信内置浏览器仍会屏蔽 xhsdiscover，此时兜底到 Web 店铺页，口令复制是那条路的最优解。
